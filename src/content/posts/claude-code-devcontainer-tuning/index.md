こんにちは。[前編](/blog/claude-code-devcontainer)では、Claude Codeをdevcontainerで隔離して全権限で自走させる環境の設計を書きました。  
今回はその続きで、実際に使い始めてから出てきた不便をどう解消したかの調整編です。

設計どおり、隔離そのものは問題なく動きました。ただ日常の道具として使い込むと、細かい不便が5つ出てきました。  
どれも設計の時点では見えていなかった、使ってみて初めて出てくるものです。順番に書きます。

## コンテナの中のClaudeだけ、URLがリンクにならない

最初に気づいた違和感はこれでした。  
手元のMacのClaude Codeは出力中のURLがクリックできるリンクになるのに、コンテナ内のClaudeだけ素のテキストのままです。地味ですが、参照URLを開くたびにコピペするのは面倒でした。

原因は環境変数でした。  
端末がリンク表示（OSC 8という仕組み）に対応しているかを、Claude Codeは`TERM_PROGRAM`などの環境変数で判定しています。  
ところがコンテナに入るときに使う`devcontainer exec`は、Macの環境変数を中へ素通ししません。  
端末そのものは同じなのに、コンテナの中から見ると`TERM_PROGRAM`が無いので、「この端末はリンク非対応」と判定されていました。

原因を調べるときは、Claude Codeの実行ファイルから判定ロジックを直接読んで当たりを付け、それでも断定はせず、設定は変えずに1回だけ実測して確定させました。  
挙動の思い込みで設定をいじり始めると、直ったときに何が効いたのか分からなくなるからです。

対処は、起動コマンドで判定を上書きする1行です。

```bash
devcontainer exec --workspace-folder . \
  --remote-env FORCE_HYPERLINK=1 \
  claude
```

`FORCE_HYPERLINK=1`は「端末判定に関係なくリンクを出せ」という指定で、これを自作の起動コマンドに組み込んで解決しました。

## スクリーンショットが渡せない

MacのClaude Codeには、クリップボードの画像をそのまま貼り付けて「このスクショのここが崩れてる」と相談できます。  
コンテナ内ではこれができませんでした。貼り付けで届くのは画像の実体ではなく、Macのファイルパスの文字列だけです。コンテナからそのパスは見えないので、開けません。

最初は、共有用のディレクトリを作って、渡したい画像をそこへコピーする形を試しました。  
動きはするのですが、「撮って、コピーして、パスを貼る」の手数が毎回かかるので定着しませんでした。  
次に考えたのがクラウド経由です。スクショ共有サービスのリンクを貼り、コンテナ側でダウンロードして開く案です。  
ただこれは前編で書いたfirewallの方式とぶつかります。このfirewallは起動時に名前解決したIPだけを通す方式で、共有サービスの画像配信はCDN上にあり、IPが入れ替わると途中から急に通らなくなります。  
画像1枚のために不安定な穴を開けるのは割に合わないのでやめました。

最終的には、スクショツール（CleanShot）の保存先ディレクトリを、読み取り専用でコンテナにマウントする形にしました。

```json
{
  "source": "${localEnv:HOME}/Library/Application Support/CleanShot/media",
  "target": "${localEnv:HOME}/Library/Application Support/CleanShot/media",
  "type": "bind",
  "readonly": true
}
```

マウント先（target）はMacとまったく同じパスにしています。  
クリップボードから貼り付けられるパス文字列が、コンテナの中でもそのまま実在するパスになるので、読み替えもコピーも要りません。撮って貼るだけで済みます。

引き換えに、撮影履歴のディレクトリ全体がコンテナから見えるようになります。  
ここは迷いましたが、読み取り専用で書き込みも削除もできないこと、ネットワークの出口が増えるわけではないことから、受け入れました。

## どちらのClaudeか見分けがつかない

Macとコンテナで同じ設定を持ち込んでいる（前編の「持ち込みはコピー」方式）ので、画面下部のステータス表示も同じです。  
つまり、開いているタブがどちらのClaudeなのか、見た目では区別がつきません。全権限で走るコンテナの方と取り違えるのは事故のもとです。

対処として、コンテナの中でだけステータス表示の先頭にバッジを出すことにしました。

```bash
if [ -f /.dockerenv ] || [ "${DEVCONTAINER:-}" = "true" ]; then
  seg "$C_ORANGE" "$FG_ONORANGE" " CONTAINER "
fi
```

`seg`はステータス表示の部品を1つ描く自作の関数です。  
コンテナの中にだけ存在する目印（`/.dockerenv`ファイルか、イメージ側で仕込んだ`DEVCONTAINER`変数）があるときだけ、オレンジ地のCONTAINERバッジを出します。  
まわりが暗い背景に白文字なので、そこだけ明暗を反転させて、視界に入れば嫌でも気づく色にしました。

### 直したのに反映されない

このバッジを作っている最中に、もうひとつ引っかかりました。  
Macでスクリプトを直したのに、コンテナの表示が古いまま変わらないのです。

原因は持ち込みの仕組みそのものでした。  
設定をコンテナへコピーする処理が走るのは、コンテナの作成時と起動時だけです。  
普段の起動コマンドがやるのは「動いているコンテナに新しいセッションで入る」ことで、コンテナを起動し直してはいません。  
修正を反映するには、コンテナを一度止めて、起動し直す必要がありました。  
コピー方式の持ち込みには、書き戻し禁止の安全と引き換えに、反映がコンテナの起動し直しまで遅れるという性質があります。

ついでに、調査でコンテナの中を直接確認したい場面が何度もあったので、起動済みコンテナにシェルで入るだけの補助コマンドも足しました。  
Claudeを通さずに中の状態を見られる入口があると、こういうトラブルの切り分けが楽になります。

## スマホからコンテナ内のセッションが見えない

Claude CodeにはRemote Controlという機能があり、動いているセッションをスマホアプリやclaude.aiのCode一覧から開いて、外から様子を見たり指示を足したりできます。  
作業を投げて放置する使い方とは相性の良い機能なのですが、Macのセッションは一覧に出るのに、コンテナ内のセッションだけ出ませんでした。

原因は設定の持ち込み方です。  
「持ち込みはコピー」の対象は指示書（CLAUDE.md）やステータス表示までで、動作設定のsettings.jsonは持ち込まず、コンテナ専用の最小限の設定を別に置いています。  
MacではRemote Controlの自動接続を有効にしていて、コンテナ専用の設定にはその1行が入っていませんでした。

対処は、コンテナ専用の設定に同じ1行を足すだけです。

```json
"remoteControlAtStartup": true
```

ひとつ注意があって、settings.jsonは「コンテナ内に無いときだけ置く」作りにしています。コンテナの中で調整した設定を、起動のたびに上書きして潰さないためです。  
そのため足した1行が効くのは新しく作るコンテナだけで、動いていた既存のコンテナでは、中のClaudeの設定画面から直接有効にしました。  
これでコンテナ内のセッションも一覧に出るようになり、放置中の作業の様子を外から確認できます。

## ビルドは成功したのに、claudeが入っていない

この環境一式は雛形にして、別のプロジェクトでも同じ構成のコンテナを使い回しています。  
その新しい環境で初回のイメージビルドが成功したのに、起動しようとすると「claudeが見つからない」というエラーになりました。

調べると、イメージの中のclaudeはなぜか500バイトのダミーファイルになっていました。  
AIを使って調べたところ、npmで配布されるClaude Codeは、まず置き場所にダミーを置き、本体のネイティブバイナリをOS・CPU別のoptionalDependenciesとして取ってきて、インストール後の処理で上書きする作りのようでした。  
ところがこのビルドではネイティブバイナリのパッケージが入っておらず、ダミーが残ったままでした。  
npmの仕様では、optional依存の取得失敗はインストール全体を失敗させません（バグではなく文書化された挙動です）。  
なのでビルドは成功で通ってしまいます。取得がなぜ失敗したのかは、結局分かっていません。

対処はDockerfileの1行です。インストールの直後に実際に実行して、壊れたイメージをビルドの時点で落とします。

```dockerfile
RUN npm install -g @anthropic-ai/claude-code@${CLAUDE_CODE_VERSION} \
  && claude --version
```

`--version`は存在チェックではなく実行なので、観測した壊れ方（ダミー残留、実行ビット無し、リンクが一時名のまま）のどれでもビルドが失敗するようになります。  
この1行は雛形にも入れたので、次に作る環境からは同じ壊れ方をビルドの時点で検知できます。  
なおesbuildなど、ネイティブバイナリをoptional依存で配るnpmパッケージは他にもあります。イメージに焼き込むものには同じ対策（インストール直後に1回実行する）がそのまま使えます。

## まとめ

- コンテナ内だけURLがリンクにならない原因は、`devcontainer exec`がMacの環境変数を渡さないこと。`--remote-env FORCE_HYPERLINK=1`で解決
- スクショはネットワークに穴を開けず、保存先ディレクトリをMacと同じパスへ読み取り専用マウント。貼り付けたパスがそのまま通る
- Macとコンテナの取り違え防止にCONTAINERバッジ。設定の持ち込みがコピー方式である以上、反映はコンテナを起動し直したタイミングになる
- コンテナ内のセッションがスマホ/claude.aiの一覧に出ない原因は、コンテナ専用のsettingsにRemote Controlの自動接続が無かったこと。`remoteControlAtStartup: true`を1行追加
- イメージのビルドが成功してもclaudeが壊れていることがある。npmがoptional依存（本体のネイティブバイナリ）の取得失敗を握りつぶすため。`claude --version`をビルドに足して検知

5つのうち4つは、Macでは意識もしていなかったものが、隔離したことでコンテナに届かなくなった、という副作用でした。  
それをコンテナに通すのか、別の経路を作るのかを一つずつ決めることになりました。最後の1つのように、環境そのものが静かに壊れていることもあります。  
作って終わりではなかった、というのが使ってみての実感です。

なお、この環境ではコンテナの中のエージェントの状態を手元のターミナル画面へ出す連携も作っているのですが、長くなるのでそれは別の記事で書く予定です。
