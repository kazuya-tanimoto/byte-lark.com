こんにちは。本サイト最初のブログ記事はこのサイトをAIで作った話にします。  
このサイト、ほぼAI（Claude Code）で作り直しました。私は全くコードを書いていません。  
どんなものを作るかをAIと壁打ちしながら決めて、AIが作ったものを評価して、イマイチなところを修正してもらう。その繰り返しでできあがりました。

ただし「いい感じに作って」の丸投げではありません。丸投げすると品質も悪く、期待したようなモノはできません。  
一定以上の品質を担保するために、AIを使った開発そのものを「仕組み」にしました。この記事はその仕組み化の話です。  
AIで開発したい人に少しでも役立つ部分があれば嬉しいです。

なお、この記事自体も AI と壁打ちしながら書いていて、事実確認も AI にやってもらっています。  
（文章もドラフトはAIに作ってもらいましたが、結局は大幅にリライトしました）

## なぜ作り直したか

元々このサイトは React で自作していました。  
フロントエンドを勉強したく、勉強と実益を兼ねて当時よさそうと思った構成（React + Storybook + 各種ライブラリ）で作っていたものです。  
勉強が目的の半分だったこともあり、新しい良いLinterを知ったら入れ替える、といった事をやっていたので完成に至らず、2025年夏に案件を2つ掛け持ちするとサイト構築は完全に止まってしまいました。。

そんな中、フリーランスで案件に参画し、仕様の定義や設計（スクラム開発のPO業務）をAIで回すうちに、サイトもAIで作ればいいんじゃね？と考えました。  
アーキテクチャなどの構成は、AIが扱いやすくトレンドも押さえたものを提案してもらい、Astro + Tailwind CSS + Cloudflare Workers になりました。

AIを使って作ろうとした背景には、こんな考えもあります。

- いまの時代、人間が手でコードを書く場面は今後ますます減っていく
- コードレビューもいずれAIだけでやるのが普通になる
- そうすると人間の仕事は「要求の定義」や「責任を引き受けること」になる（多分）
- だからモノ作りはAIに任せるのが良いのでは？

## AIで開発することの速度
実際にAIに開発を任せてみると、その速度に驚きました。  
速さはコミット履歴がそのまま示しています。

### 最初のサイト
2021/12に個人事業主開始にあたりHPが必要と考え、Hugo（SSG）で簡易ないサイトを作成しました。所要期間は約2週間。  
とりあえずサイト公開。が目的だったのでこだわりもなく、大した内容はありませんでした。

### Reactで自作
その後Reactを勉強したいと考え、勉強＋実益を狙って React+Storybook  種ライブラリでサイトを作り始める。  
確かに勉強にはなったし、参画した案件でも役に立ちましたが、サイト公開という目的に対してはTooMuchだった事もあり、遅々として進まず。  
2025/07から2案件の掛け持ちで稼働が増え、全く進まなくなる。結果2年あまりかけて未完成でした。。

### AIで作り直し
前述の通り、PO業務をAIで回す中で、AIを使ったサイト構築をやってみようと思いたち実行。  
AIイチからで作り直して全ページ作成まで6週間です。  
ネットの記事などでは、1日で作ったとか、バズりそうな記事がありますが、ぶっちゃけフルタイムで稼働しながらそんなことできません。  
（家族との時間も大切にしたいし）

で、結果これぐらいの期間でサイト公開に漕ぎ着けたわけですが、それでも数年完成しなかったものが数週間で形になったスピード感は「段違い」の経験でした。  
AIってすごい。

## AIに任せられない

ただしAIに任せきりにすると、だいたい次のような事で品質も低下し、ストレスが溜まる要因になりました。

- 過剰実装になりがち：すごいエッジケースを考慮した実装とかし始める。で、ゴリゴリコード量増える。個人サイトなんだからそんなのいらないって。
- 記憶が飛ぶ：会話のセッションを跨ぐと当然だけど前回を覚えていない。同じセッションでもやり取り長くなると記憶喪失になりがち。さっきのやり取りはよ？
- セッションの品質低下：やり取りが長くなると目に見えて品質が落ちる。Opus使っててもボロいものはボロい
- 確認を飛ばす：「完了しました」と言うのに、確認したか聞くと「正直に言うとやっていません。今すぐやります」と。これは「定型文か」って思うほど言われてゲンナリしました。セッション長くなると起こりがち。

こういった問題を仕組みで改善しました。  
当然今でも問題はあるけど、随時試行錯誤して改善する事で徐々に成功率は上がってきたと思います。
色々試してはやめて、、を繰り返した中で、比較的効果の合ったものを紹介します。

## 1：タスクを小さく刻む

別のリポジトリで、AI とのやり取りが長くなるほど品質が落ちるのを何度も経験しました。  
気を抜くと頼んでいない所まで作り込む過剰実装もよくありました。  
個人のプロダクトなのに開発途中でコード量20万行超えになったり。絶対いらない。

なので1タスクを徹底的に小さくしました。
PBI(プロダクトバックログアイテム)を小さく定義し、サクッと終わる程度のPBIをたくさん作りました。
で、1セッションでは1PBIだけ対応し、完了すると新規セッションで次のPBIを対応します。  
仕事は細かく刻む。これだけです。

## 2：設計メモと進捗一覧

PBIを作り始める前に、設計用の全体像をメモに纏めたのと、PBIを作りながら、進捗管理用の一覧を作りました。

- 設計メモ：何を・どんな順で・どんな方針で作るかを1文書に。AI が毎セッションの最初に読む資料。大まかな方針、地図がないとブレる事を防ぐ目的です
- 進捗一覧：全タスクが「未着手 / 作業中 / 完了」のどれかを1枚で管理します。複数セッションで進めるので、管理しないとすぐ訳が分からなくなる。セッションを跨ぐと記憶もなくなるし、自分で状況を記憶するのも無理があるので、状況把握目的です

人間だけで回す開発プロジェクトと、何となく同じようなことやってます。

## 3：完了前のチェックリスト

AIから「完了です。〇〇も対応済みです」と報告あり→「完了にしたなら△△も確認したよね?」と聞く→「いえ、やっていません。今すぐやります」  
これが日常茶飯事で発生してました。

その時詰めても、次のセッションだと当然のように繰り返すので、完了の前に必ず通す確認をルール化しました。  
各タスクの条件に、こういうチェックを常設しています。

```md
- [ ] 手元でスクショ確認（PC + スマホ幅）
- [ ] 公開前プレビューでスクショ確認
- [ ] 自動テストが すべて通る
```

これを満たさないとタスクを完了にできません。しかも、この確認項目を書き忘れたタスクは機械的に検出されます。人の注意力には頼らない方針です。

## それでもAI任せには限界がある

仕組みを敷いても、人間が出ていく場面は残ります。

このサイトでは「憶測で答えず、必ず事実を確認してから答える」というルールを AI に課しています。全体ルールはこんな調子で書いてあります。

```md
# CLAUDE.md（全体ルールの一部）
- 憶測で答えない。一次情報（ツール実行結果・ソース・公式 docs）を確認してから答える
- 私に忖度せず、フラットに評価して提案する
```

それでも、確認する元の情報そのものにノイズが混じることがあります。経歴データで実際にありました。古いスキルシートが求人サービスのテンプレートを下敷きにしていて、テンプレートの「記入例」（架空の人物の職歴）がファイルに残っていたのです。AI が素直に読むと、他人の記入例まで私の実績として取り込みかねませんでした。これは見抜いて除外しました。一次情報を確認させても、それを見極めるのは結局人間の仕事です。

技術面でも似た例が。ある記事を消したら、自動テストは緑なのに本番ビルドだけ「消したはずの画像が見つからない」で赤になりました。本番側が前回のビルド結果をキャッシュしていて、古い情報が残っていたのが原因です。環境ごとにキャッシュが違うと手元で再現しないので、ログを1つずつ読んで突き止めるしかありませんでした。

だからこのやり方には向き不向きがあります。

- 向く人：AI の答えを評価して「それは違うのでは」と見抜ける／イマイチを都度直せる／コストをかけられる／コードより成果に満足を感じる
- 向かない人：コードを書くのが何より楽しい／真偽を評価できず言いなりになる／コストをかけたくない

## 会話が長いと、AIは指示を忘れる

一番性能の良いモデル（Opus）でも、会話の文脈が2割ほど埋まると品質が落ち始めます。長くなると、全体ルール（CLAUDE.md）の内容すら忘れていきます。

調べると裏付けがありました。「Lost in the Middle」という研究で、言語モデルは文脈の最初と最後はよく拾うが真ん中は取りこぼす、という傾向が複数のモデルで確認されています。会話が長くなると、最初の指示が真ん中に埋もれて効きにくくなるわけです。公式ドキュメントにも「文脈が埋まると性能が落ち、以前の指示を忘れ始める」「書きすぎたルールファイルはかえって無視される」とあります。

対処はこうしました。

- 気になるルール（例「忖度せずフラットに評価して」）は、その都度プロンプトの「いまこの場」で打ち直す
- よく使う定型文はスニペットに登録して一瞬で入力する

これも、研究が勧める対処「重要な指示は文脈の最初か最後に置け」と一致していました。

## 自走しきれない——いまの課題と次の一手

いまの一番の不満は、AI が自分だけで走りきれないことです。

安全のため、AI は隔離された環境（サンドボックス）で動かしています。変なものを壊される心配がないのは安心です。ただ制限が強く、開発サーバーの起動すら私が手で打ったり、コマンドやファイル書き込みのたびに承認を求められたりします。そこで止まる。正直、AI が進むのを見守るのは楽しくないので、自走してラクをさせてくれる方がありがたいです。

当初は「AI 専用の壊れてもいい PC を1台用意して全権限で動かす」案も考えましたが、調べ直すと筋が悪い。実機の OS や認証情報がそのまま晒され、隔離としては弱いからです。筋の良い方向はこうでした。

- サンドボックスは使ったまま、詰まるところだけ設定でピンポイントに開ける
- 放置で長く回すときは、公式の隔離コンテナ（外部通信を遮断する仕組み入り）の中で動かす

これなら母艦の OS と認証情報を守りつつ自走させられます。専用 PC より安全で確実です。近いうちに手を入れたいところです。

## やってみてどうだったか

率直な感想です。

- 速度は段違い。数年動かなかったものが数週間で形になった
- モチベが続く。コードを書くこと自体が無上の喜びではないので、完成に近づく手応えが嬉しい。AI だとそれが早いので続けられる
- コスト：いまは上位プラン。以前は下位プランで数時間ごと・週ごとの制限にすぐ当たり中断が多かったが、上位にして止まらなくなった。「時間を買っている」と思って払う
- モデルは一番良いものを使う。手戻りが少なく結局ラク。公式ドキュメントも「迷ったら複雑な作業は最上位のモデルから」と勧めている
- 品質：コードは前の自作版も劣っていない（都度リファクタしていた）。差が出るのはこれから、デザインを AI でブラッシュアップする段階

## 最後に責任を持つのは人間

AI で作っていても、出来たものの責任を引き受けるのは自分以外にいません。自分のプロダクトなのだから、中身をチェックするのも、ダメな所を直させるのも当たり前です。さっきの「他人の記入例を混ぜない」もその1つでした。

これは個人開発に限りません。いま入っている案件でも、結局は「オーナーシップを持って仕事しているか」に尽きます。仕様も不具合も進捗も、自分以外のメンバーの担当でも、プロダクトに関わるなら自分事として関わる。AI 駆動開発でも同じで、実装を AI に任せても、要求を定義し、結果を評価し、責任を引き受けるのは人間です。だからこのやり方は「AI の言うことの正しさを見抜ける人」に向いています。

## まとめ：これから試す人へ

AI に開発を任せるのは、私にとってもう外せない選択肢です。肝は「任せきり」ではなく「仕組みに乗せる」こと。

- タスクを小さく刻む
- 設計メモと進捗一覧を持つ
- 完了の前に必ず確認させる

もう1つ、重要な文脈は消えないように残すこと。設計メモも進捗一覧も、この記事の取材メモも文書にしています。AI は会話が長いと忘れ、セッションを跨ぐと別人になるので、人の頭の中ではなく読まれる場所に置いておく。

ちなみにこの記事は AI と壁打ちしながら書いたのですが、途中で AI に公式ドキュメントを調べてもらったら、ここで挙げた仕組みの多くがそのまま推奨されていました。私自身は公式を読んでいません。やってきたことは、方向として間違っていなかったようです。

合う人はどんどんやればいいと思います。コードを書く喜びより、出来上がる成果に満足を感じるなら、AI はものづくりを大きく加速してくれます。
