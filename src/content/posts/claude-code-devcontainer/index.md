こんにちは。今回は Claude Code に全権限を渡して自走させる環境を devcontainer で作った話です。

Claude Code には `--dangerously-skip-permissions` というオプションがあります。  
名前の通り危険側のオプションで、ファイル編集もコマンド実行もいちいち許可を求めず、AIが最後まで勝手に進めます。  
作業を投げて放置できるので魅力的なのですが、普段使いの Mac（以下、母艦と呼びます）でこれをやるのはさすがに怖くてできませんでした。何かあったときに壊れるのが自分の普段の環境だからです。

調べた結果、全権限で自走させるなら隔離した環境を別に用意するしかない、という結論になりました。  
隔離環境自体は、Anthropic 公式の雛形をベースにすれば現実的な手間で作れます。  
この記事はその設計編で、なぜ devcontainer にしたのか、何を守るためにどう作ったのかを書きます。  
実際に使い始めてからの細かい調整（こちらも結構ありました）は[後編](/blog/claude-code-devcontainer-tuning)に分けています。

## そもそも何に困っていたか

母艦の Claude Code は、標準のサンドボックス（macOS の Seatbelt という仕組み）の中でコマンドを実行します。  
安全側に倒した作りなので、開発作業では詰まりが出ます。私の場合はこの 3 つでした。

- `yarn add` などパッケージ取得系が名前解決の段階で失敗する
- E2E テスト（Playwright）のブラウザが起動できない
- 許可を求めるプロンプトが頻発し、放置して任せることができない

設定の緩和でしのいでいましたが、緩和した分だけ母艦の防御は薄くなります。  
詰まるたびに穴を開けるやり方には限界を感じていました。

## 「壊れてもいいPC」案はやめた

最初に考えたのは、Claude 専用に壊れてもいい PC を用意してフル権限で走らせる案です。これは調べた上でやめました。  
隔離の境界がその PC の OS 自身になるので、OS の設定やそこに置いた認証情報には Claude がそのまま触れます。  
それに、使い込むうちに設定やデータが溜まって、結局「壊れたら困るPC」になりそうでした。

Anthropic の公式ドキュメントも、`--dangerously-skip-permissions` を使うならコンテナや VM の中で、という立場です（[Claude Code のサンドボックス解説](https://code.claude.com/docs/en/sandboxing)）。  
「標準のサンドボックスがあるから大丈夫では？」と思っていた時期もありましたが、あれが縛るのは Bash の実行だけで、ファイル編集などは対象外です。  
全権限で放置するなら、OS の外側に別の境界を用意する必要があります。

## devcontainer で隔離する

採用したのは devcontainer です。  
Anthropic が Claude Code のリポジトリで[公式の雛形](https://github.com/anthropics/claude-code/tree/main/.devcontainer)を公開していて、設計の骨格はこれをベースにしました。  
やっていることは大きく 3 つです。

- コンテナから見える母艦のファイルは、作業対象のリポジトリだけ（bind mount）
- Claude の設定とログイン状態はコンテナ専用の volume に永続化（初回 1 回ログインすれば済む）
- 起動時に firewall を張り、外向きの通信を許可した宛先だけに絞る（default-deny）

リポジトリは git 管理下なので、コンテナ内で何が起きても復旧できます。  
母艦のホームディレクトリや認証情報は、そもそもコンテナから見えません。

## 自分の環境向けに決めたこと

雛形をそのまま使うだけでなく、自分の環境に合わせてルールをいくつか決めました。

### 設定の持ち込みはコピー、書き戻しは禁止

コンテナの中でも母艦と同じ指示書（グローバルの CLAUDE.md）を使いたいので、設定は持ち込みます。  
ただし母艦の設定ディレクトリを書き込み可でマウントすることはしません。理由は権限昇格です。  
コンテナ内の Claude が母艦側の設定（hooks など、Claude 起動時に実行されるもの）を書き換えられると、次に母艦で Claude を起動した瞬間にそれが実行されます。  
これができてしまうと、隔離した意味がなくなります。

そこで母艦の設定は読み取り専用でマウントし、起動時にコンテナ内へコピーする方式にしました。

```json
"mounts": [
  "source=claude-code-config-${devcontainerId},target=/home/node/.claude,type=volume",
  "source=${localEnv:HOME}/dotfiles/claude,target=/mnt/host-claude,type=bind,readonly"
]
```

読み取り専用（readonly）なので、コンテナからは書き戻せません。

### 認証情報は漏れても被害が限られる形だけ

SSH 鍵や macOS のキーチェーンはコンテナに入れません。  
git push には GitHub の fine-grained PAT（対象リポジトリ 1 つ・contents の read/write のみに絞ったトークン）を使い、コンテナ内で 1 回だけ `gh auth login` して専用 volume に永続化します。  
母艦のディスクにも環境変数にもイメージにも PAT は残りません。

漏れないようにしきるのは無理だと思っているので、漏れたときの被害が小さくなる形にしています。  
このトークンで触れるのは公開リポジトリ 1 つの中身だけで、他のリポジトリにもアカウント設定にも手が届きません。

### 通信は許可した宛先だけ

firewall は公式雛形の方式を引き継ぎました。  
iptables で外向き通信を全部落とし、許可リストに載せた宛先だけ通します。

```bash
iptables -P OUTPUT DROP
iptables -A OUTPUT -m set --match-set allowed-domains dst -j ACCEPT
```

許可リストに入れているのは GitHub の IP 帯（公式 API から動的取得）、npm や Playwright の取得先など、開発に必要な宛先だけです。  
起動のたびに自己検証も走らせていて、「example.com に到達できないこと」と「api.github.com に到達できること」の両方を確認します。  
この確認が通らなかったら自走はさせない運用にしています。

### firewall は完全ではない

正直に書くと、この firewall は完全な出口対策ではありません。  
設定ファイルの書式はドメイン名ですが、実際に許可されるのは起動時に名前解決した IP アドレスです。  
通信時のホスト名は見ていないので、許可した IP に別のサイトが相乗りしていれば通ります。CDN のエッジがまさにそうです。

なので「雑な悪用や大量の持ち出しを止める網」くらいの位置づけに割り切っています。  
完全な出口制限が必要な作業は、そもそもこのコンテナではやりません。

## 使い勝手

初回だけイメージのビルドで数分待ち、Claude へのログインが 1 回要ります。  
以後は自作の起動コマンド一発で、母艦とほぼ同じ操作感です。  
起動コマンドには、firewall の自己検証が通っていなければ起動しないチェックを入れました。  
firewall の初期化はこけてもコンテナ自体は動き続けてしまうので、起動できたからといって安全とは限らないからです。

この環境にしてから、母艦で詰まっていた `yarn add` も E2E テストも普通に通るようになりました。  
夜に作業を投げて朝に結果を見る、という使い方ができています（これがやりたかった）。

## まとめ

- 全権限で自走させるなら隔離環境が要る。公式もコンテナ / VM の中でという立場
- 母艦への書き戻しをさせない。認証情報は漏れても被害が限られる形だけ。通信は許可した宛先だけ
- firewall で守れる範囲は限られるので、そこは割り切って使う

ここまでが設計の話です。  
実際に使い始めると「コンテナの中の Claude だけ URL がリンクにならない」「スクリーンショットが渡せない」といった、設計時には見えなかった細かい不便が出てきました。その潰し込みは[後編](/blog/claude-code-devcontainer-tuning)に書きます。
