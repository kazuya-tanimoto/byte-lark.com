こんにちは。今回はClaude Codeに全権限を渡して自走させる環境をdevcontainerで作った話です。

Claude Codeには`--dangerously-skip-permissions`というオプションがあります。  
付けると、Claudeはファイル編集もコマンド実行もいちいち確認せずに最後まで進めます。  
作業を丸ごと投げて放置できるので魅力的なのですが、裏を返すと、ファイルの削除のような取り返しのつかない操作も、そのまま実行されるということです。  
普段使いのMacでこれをやるのはさすがに怖くてできませんでした。何かあったときに壊れるのが自分の普段の環境だからです。

調べた結果、全権限で自走させるなら隔離した環境を別に用意するしかない、という結論になりました。  
隔離環境自体は、Anthropic公式の雛形をベースにすれば現実的な手間で作れます。  
この記事はその設計編で、devcontainerを選んだ理由と、作るときに決めたことを書きます。  
実際に使い始めてからの細かい調整（こちらも結構ありました）は[後編](/blog/claude-code-devcontainer-tuning)に分けています。

## 困っていたこと

手元のMacのClaude Codeは、macOSのサンドボックスの中でコマンドを実行します。  
制限が強めの作りなので、開発作業では詰まりが出ます。私の場合はこの3つでした。

- `yarn add`などパッケージを取ってくるコマンドが、外部への通信を止められて失敗する
- E2Eテスト（Playwright）のブラウザが起動できない
- ファイル編集やコマンド実行のたびに許可を求められる

設定に穴を開ければ通るものもありますが、あまり穴を開けるとサンドボックスの意味が無くなると考え、やりませんでした。  
かわりに、詰まるたびに別のターミナルで自分がコマンドを実行したり、許可を出したりしていました。  
結果的に、作業を投げたつもりでも、結局ターミナルに張り付くことになります。

張り付きをなくすには、`--dangerously-skip-permissions`で確認を切るしかありません。  
かといって、冒頭に書いたとおり普段使いのMacで確認を切るのは怖くてできません。  
そこで、Claude Code専用のMacを別に用意することを考え始めました。

## 「専用Mac」案はやめた

最初に考えたのは、Claude専用に、最悪壊れてもいいMacを用意し、その上でフル権限で走らせる案ですが、これは調べた上でやめました。  
そのMacの中にはClaudeを止めるものが何もないので、OSの設定も、git pushのためにMacへ置く認証情報も、そのままLLMが触れてしまいます。  
それに、使い込むうちに設定やデータが溜まって、結局「壊れたら困るMac」になりそうでした。

Anthropicの公式ドキュメントも、`--dangerously-skip-permissions`を使うならコンテナやVMの中で、という立場です（[Claude Codeのサンドボックス解説](https://code.claude.com/docs/en/sandboxing)）。  
壊れてもいい環境は、Macを1台丸ごと用意するのではなく、コンテナやVMで区切って作ることにしました。

## devcontainerで隔離する

採用したのはdevcontainerです。  
AnthropicがClaude Codeのリポジトリで[公式の雛形](https://github.com/anthropics/claude-code/tree/main/.devcontainer)を公開していて、設計の骨格はこれをベースにしました。  
やっていることは大きく3つです。

- コンテナから見える手元のMacのファイルは、作業対象のリポジトリだけ（bind mount）
- Claudeの設定とログイン状態はコンテナ専用のvolumeに永続化（初回1回ログインすれば済む）
- 起動時にfirewallを張り、外向きの通信を許可した宛先だけに絞る（default-deny）

リポジトリはgit管理下なので、コンテナ内で何が起きても復旧できます。  
手元のMacのホームディレクトリや認証情報は、そもそもコンテナから見えません。

## 自分の環境向けに決めたこと

雛形をそのまま使うだけでなく、自分の環境に合わせてルールをいくつか決めました。

### 設定の持ち込みはコピー、書き戻しは禁止

コンテナの中でも手元のMacと同じ指示書（グローバルのCLAUDE.md）を使いたいので、設定は持ち込みます。  
ただしMac側の設定ディレクトリを書き込み可でマウントすることはしません。  
コンテナ内のClaudeがMac側の設定（hooksなど、Claude起動時に実行されるもの）を書き換えられると、次にMacでClaudeを起動した瞬間にそれが実行されます。  
これができてしまうと、隔離した意味が無くなります。

そこでMac側の設定は読み取り専用でマウントし、起動時にコンテナ内へコピーする方式にしました。

```json
"mounts": [
  "source=claude-code-config-${devcontainerId},target=/home/node/.claude,type=volume",
  "source=${localEnv:HOME}/dotfiles/claude,target=/mnt/host-claude,type=bind,readonly"
]
```

読み取り専用（readonly）なので、コンテナからは書き戻せません。

### 認証情報は漏れても被害が限られる形だけ

SSH鍵やmacOSのキーチェーンはコンテナに入れません。  
git pushにはGitHubのfine-grained PATを使います。トークンはリポジトリごとに払い出し、権限は最小のcontents read/writeから始めて、運用上必要になった分だけ足しています。  
コンテナ内で1回だけ`gh auth login`して専用volumeに永続化します。  
手元のMacのディスクにも環境変数にもイメージにもPATは残りません。

万が一PATが漏れた場合のことを考え、漏れたときの被害が小さくなる形にしています。  
このトークンで操作できるのはこの公開リポジトリ1つだけで、他のリポジトリやアカウント設定には使えません。

### 通信は許可した宛先だけ

firewallは公式雛形の方式を引き継ぎました。  
iptablesで外向き通信を全部落とし、許可リストに載せた宛先だけ通します。

```bash
iptables -P OUTPUT DROP
iptables -A OUTPUT -m set --match-set allowed-domains dst -j ACCEPT
```

許可リストに入れているのはGitHubのIP帯（公式APIから動的取得）、npmやPlaywrightの取得先など、開発に必要な宛先だけです。

ただ、firewallの初期化に失敗しても、コンテナ自体は普通に動き続けてしまいます。  
全権限で自走させる前提はこのfirewallなので、張れているか分からないまま走らせるわけにはいきません。  
そこで起動のたびに自己検証を走らせ、「example.comに到達できないこと（遮断が効いている）」と「api.github.comに到達できること（許可が効いている）」の両方を確認します。  
自作の起動コマンドは、この検証が通らない限りClaudeを起動しない作りにしています。

### firewallは完全ではない

正直に書くと、このfirewallは完全な出口対策ではありません。  
設定ファイルの書式はドメイン名ですが、実際に許可されるのは起動時に名前解決したIPアドレスです。  
通信時のホスト名は見ていないので、許可したIPに別のサイトが相乗りしていれば通ります。CDN（複数のサイトが配信サーバーを共有する仕組み）がまさにそうです。

なので、雑な悪用や大量の持ち出しを止められれば十分、と割り切っています。  
完全な出口制限が必要な作業は、そもそもこのコンテナではやりません。

## 使い勝手

初回だけイメージのビルドで数分待ち、Claudeへのログインが1回要ります。  
以後は自作の起動コマンド一発で、手元のMacとほぼ同じ操作感です。

この環境にしてから、手元のMacで詰まっていた`yarn add`もE2Eテストも普通に通るようになりました。  
作業を投げてしばらく放置する、という使い方ができています（これがやりたかった）。

## まとめ

- 全権限で自走させるなら隔離環境が要る。公式もコンテナ/VMの中でという立場
- 手元のMacへの書き戻しをさせない。認証情報は漏れても被害が限られる形だけ。通信は許可した宛先だけ
- firewallで守れる範囲は限られるので、そこは割り切って使う

ここまでが設計の話です。  
実際に使い始めると「コンテナの中のClaudeだけURLがリンクにならない」「スクリーンショットが渡せない」といった、設計時には見えなかった細かい不便が出てきました。それらの改善の試行錯誤は[後編](/blog/claude-code-devcontainer-tuning)に続きます。
