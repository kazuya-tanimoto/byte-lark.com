こんにちは。[前編](/blog/claude-code-devcontainer)では、Claude Code を devcontainer に閉じ込めて全権限で自走させる環境の設計を書きました。今回はその続きで、実際に使い始めてから出てきた不便をどう潰したかの調整編です。

設計どおり、隔離そのものは問題なく動きました。ただ日常の道具として使い込むと、細かい不便が 3 つ出てきました。面白いのは、3 つとも原因をたどると同じところに行き着くことです。壁を作ったのは自分なのに、母艦（普段使いの Mac）では当たり前に届いていたものが壁の内側に届かなくなっていて、それに気づいていませんでした。

## その1：コンテナの中のClaudeだけ、URLがリンクにならない

最初に気づいた違和感はこれでした。母艦の Claude Code は出力中の URL がクリックできるリンクになるのに、コンテナ内の Claude だけ素のテキストのまま。地味ですが、参照 URL を開くたびにコピペするのは効きます。

原因は環境変数でした。端末がリンク表示（OSC 8 という仕組み）に対応しているかを、Claude Code は `TERM_PROGRAM` などの環境変数で判定しています。ところがコンテナに入るときに使う `devcontainer exec` は、母艦の環境変数を中へ素通ししません。コンテナの中から見ると `TERM_PROGRAM` が存在しないので、「この端末はリンク非対応」と判定されていました。端末は同じものを使っているのに、です。

このときの調べ方は少し丁寧にやりました。Claude Code の実行ファイルから判定ロジックを直接読んで当たりをつけ、それでも断定はせず、設定を変えずに 1 回だけ実測して確定させています。挙動の思い込みで設定をいじり始めると、直ったときに何が効いたのか分からなくなるからです。

対処は、起動コマンドで判定を上書きする 1 行です。

```bash
devcontainer exec --workspace-folder . \
  --remote-env FORCE_HYPERLINK=1 \
  claude
```

`FORCE_HYPERLINK=1` は「端末判定に関係なくリンクを出せ」という指定で、これをコンテナ起動用の自作コマンドに組み込んで解決しました。

## その2：スクリーンショットが渡せない

母艦の Claude Code には、クリップボードの画像をそのまま貼り付けて「このスクショのここが崩れてる」と相談できます。コンテナ内ではこれができませんでした。貼り付けで届くのは画像の実体ではなく、母艦側のファイルパスの文字列だけ。コンテナからそのパスは見えないので、開けません。

最初はクラウド経由を考えました。スクショ共有サービスのリンクを貼り、コンテナ側でダウンロードして開く案です。ただこれは前編で書いた firewall の割り切りと正面衝突しました。この firewall は起動時に名前解決した IP だけを通す方式で、共有サービスの画像配信は CDN 上にあり、IP が入れ替わると途中から急に通らなくなります。画像 1 枚のために不安定な穴を開けるのは割に合わず、打ち切りました。共有用ディレクトリに毎回コピーする案も試しましたが、「撮る → コピーする → パスを貼る」の手数が残る時点で、日常の道具にはなりません。

落ち着いた先は、スクショツール（CleanShot）の保存先ディレクトリを、読み取り専用でコンテナにマウントすることでした。

```json
{
  "source": "${localEnv:HOME}/Library/Application Support/CleanShot/media",
  "target": "${localEnv:HOME}/Library/Application Support/CleanShot/media",
  "type": "bind",
  "readonly": true
}
```

ポイントはマウント先（target）を母艦とまったく同じパスにしたことです。クリップボードから貼り付けられるパス文字列が、コンテナの中でもそのまま実在するパスになるので、読み替えもコピーも要りません。撮って、貼るだけです。

引き換えに、撮影履歴のディレクトリ全体がコンテナから見えるようになります。ここは迷いましたが、読み取り専用で書き込みも削除もできないこと、ネットワークの穴と違って出口が増えるわけではないことから、受け入れました。前編と同じで、何を晒して何を守るかを決めるのが設計だと思っています。

## その3：今どっちで喋っているのか分からない

母艦とコンテナで同じ設定を持ち込んでいる（前編の「持ち込みはコピー」方式）ので、画面下部のステータス表示も同じです。つまり、開いているタブが母艦の Claude なのかコンテナの Claude なのか、見た目では区別がつきません。全権限で走る側と母艦側を取り違えるのは事故のもとです。

対処は、コンテナの中でだけステータス表示の先頭にバッジを出すことにしました。

```bash
# Segment 0: devcontainer badge — 母艦では出さない
if [ -f /.dockerenv ] || [ "${DEVCONTAINER:-}" = "true" ]; then
  printf "${BG_ORANGE}${FG_ONORANGE} CONTAINER ${RESET}"
fi
```

コンテナの中にだけ存在する目印（`/.dockerenv` ファイルか、イメージ側で仕込んだ `DEVCONTAINER` 変数）を見て、あればオレンジ地の CONTAINER バッジを出します。まわりが暗い背景に白文字なので、そこだけ明暗を反転させて、視界に入れば嫌でも気づく色にしました。

### 「直したのに反映されない」の罠

このバッジを作っている最中に、もうひとつ教材になる罠を踏みました。母艦側でスクリプトを直したのに、コンテナの表示が古いまま変わらないのです。

原因は持ち込みの仕組みそのものでした。母艦の設定をコンテナへコピーする処理は、コンテナの作成時にしか走りません。そして普段の起動コマンドがやるのは「動いているコンテナに新しいセッションで入る」ことで、コンテナを作り直してはいません。つまり修正を反映するには、コンテナを一度止めて作り直す必要がありました。コピー方式の持ち込みは、書き戻し禁止の安全と引き換えに「反映はコンテナの作り直しのタイミング」という性質を持ちます。これを分かって使わないと、直したはずの設定を前に首をひねることになります。

ついでに、調査でコンテナの中を直接覗きたい場面が何度もあったので、起動済みコンテナにシェルで入るだけの補助コマンドも足しました。Claude を通さずに中の状態を確認できる入口は、こういうトラブルの切り分けでそのまま効きます。

## まとめ

- コンテナ内だけ URL がリンクにならない原因は、`devcontainer exec` が母艦の環境変数を渡さないこと。`--remote-env FORCE_HYPERLINK=1` で解決
- スクショはネットワークに穴を開けず、保存先ディレクトリを母艦と同じパスへ読み取り専用マウント。貼り付けたパスがそのまま通る
- 母艦とコンテナの取り違え防止に CONTAINER バッジ。設定の持ち込みがコピー方式である以上、反映はコンテナ作り直しのタイミングになる

3 つとも、壁を作ったこと自体の副作用でした。隔離環境は「作って終わり」ではなく、母艦なら黙って届いていたものを棚卸しして、通すもの・通さないもの・別の経路にするものを一つずつ決めていく作業が本体だった、というのが使い込んでみての実感です。

なお、この環境ではコンテナの中のエージェントの状態を母艦側のターミナル画面へ出す連携も作っているのですが、長くなるのでそれは別の記事で書く予定です。
