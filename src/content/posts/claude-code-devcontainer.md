こんにちは。今回は Claude Code をコンテナに閉じ込めて、全権限で自走させる環境を作った話です。

Claude Code には `--dangerously-skip-permissions` というオプションがあります。名前の通り危険側のオプションで、ファイル編集もコマンド実行もいちいち許可を求めず、AIが最後まで勝手に進めます。作業を投げて放置できるので魅力的なのですが、普段使いの Mac（以下、母艦と呼びます）でこれをやる勇気はありませんでした。暴走したときに壊れるのが、自分の実環境そのものだからです。

結論から書くと、全権限の自走は隔離とセットでやるものです。そして隔離環境は、Anthropic 公式の雛形をベースにすれば現実的な手間で作れます。この記事はその設計編で、なぜコンテナに閉じ込めるのか、何を守るためにどう作ったのかを書きます。実際に使い始めてからの細かい調整（こちらも結構ありました）は[後編](/blog/claude-code-devcontainer-tuning)に分けています。

## そもそも何に困っていたか

母艦の Claude Code は、標準のサンドボックス（macOS の Seatbelt という仕組み）の中でコマンドを実行します。安全側に倒した作りなので、開発作業では詰まりが出ます。私の場合はこの 3 つでした。

- `yarn add` などパッケージ取得系が名前解決の段階で失敗する
- E2E テスト（Playwright）のブラウザが起動できない
- 許可を求めるプロンプトが頻発し、放置して任せることができない

設定の緩和でしのいでいましたが、緩和はそのまま母艦の防御を薄くすることでもあります。「詰まるたびに穴を開ける」方向には限界がありました。

## 「壊れてもいいPC」案はやめた

最初に考えたのは、Claude 専用の壊れてもいい PC を用意してフル権限で走らせる案です。これは調べた上でやめました。隔離の境界が実 OS 自身になるので、その PC の OS と、そこに置いた認証情報は結局そのまま晒されるからです。「壊れてもいい」つもりの環境は、使い込むほど壊れると困る環境になっていきます。

Anthropic の公式ドキュメントも、`--dangerously-skip-permissions` を使うならコンテナや VM の中で、という立場です（[Claude Code のサンドボックス解説](https://code.claude.com/docs/en/sandboxing)）。「標準のサンドボックスがあるから大丈夫では？」と思っていた時期もありましたが、あれが縛るのは Bash の実行だけで、ファイル編集などは対象外です。全権限で放置するなら、境界は OS の外側に別途用意する必要があります。

## devcontainer に閉じ込める

採用したのは devcontainer です。Anthropic が Claude Code のリポジトリで[公式の雛形](https://github.com/anthropics/claude-code/tree/main/.devcontainer)を公開していて、設計の骨格はこれをベースにしました。仕掛けは大きく 3 つです。

- コンテナから見える母艦のファイルは、作業対象のリポジトリだけ（bind mount）
- Claude の設定とログイン状態はコンテナ専用の volume に永続化（初回 1 回ログインすれば済む）
- 起動時に firewall を張り、外向きの通信を「許可した宛先だけ」に絞る（default-deny）

リポジトリは git 管理下なので、最悪コンテナ内で何かが暴れても復旧できます。母艦のホームディレクトリや認証情報は、そもそも見えません。

## 何を守るか：3つの原則

雛形をそのまま使うだけでなく、自分の環境に合わせて原則を決めました。

### 持ち込みはコピー、書き戻しは禁止

コンテナの中でも母艦と同じ指示書（グローバルの CLAUDE.md）を使いたいので、設定は持ち込みます。ただし母艦の設定ディレクトリを書き込み可でマウントすることはしません。理由は権限昇格です。コンテナ内の暴走が母艦側の設定（hooks など、Claude 起動時に実行されるもの）を書き換えられると、次に母艦で Claude を起動した瞬間にそれが実行されます。それを許すと、せっかくの隔離が意味を失います。

そこで母艦の設定は読み取り専用でマウントし、起動時にコンテナ内へコピーする方式にしました。

```json
"mounts": [
  "source=claude-code-config-${devcontainerId},target=/home/node/.claude,type=volume",
  "source=${localEnv:HOME}/dotfiles/claude,target=/mnt/host-claude,type=bind,readonly"
]
```

読み取り専用（readonly）なので、コンテナからは何をどうやっても書き戻せません。

### 認証情報は「漏れても被害が限られる」形だけ

SSH 鍵や macOS のキーチェーンはコンテナに入れません。git push には GitHub の fine-grained PAT（対象リポジトリ 1 つ・contents の read/write のみに絞ったトークン）を使い、コンテナ内で 1 回だけ `gh auth login` して専用 volume に永続化します。母艦のディスクにも環境変数にもイメージにも PAT は残りません。

ポイントは「漏れない」を目指すのではなく、漏れたときの被害範囲を先に限定しておくことです。このトークンで触れるのは公開リポジトリ 1 つの中身だけで、他のリポジトリにもアカウント設定にも手が届きません。

### 通信は「許可した宛先だけ」

firewall は公式雛形の方式を引き継ぎました。iptables で外向き通信を全部落とし、許可リストに載せた宛先だけ通します。

```bash
iptables -P OUTPUT DROP
iptables -A OUTPUT -m set --match-set allowed-domains dst -j ACCEPT
```

許可リストは GitHub の IP 帯（公式 API から動的取得）、npm や Playwright の取得先など、開発に必要な宛先だけです。さらに起動のたびに自己検証が走り、「example.com に到達できないこと」と「api.github.com に到達できること」の両方を確認します。これが通らない限り、自走はさせません。

### firewall は完全ではない、と知って使う

正直に書いておくと、この firewall は完全な出口対策ではありません。設定ファイルの書式はドメイン名ですが、実際に許可されるのは起動時に名前解決した IP アドレスです。通信時のホスト名は見ていないので、許可した IP に別のサイトが相乗りしていれば通ります。CDN のエッジはまさにそういう場所です。

なので位置づけは「雑な悪用や大量の持ち出しを止める網」と割り切っています。完全な出口制限が必要な作業は、そもそもこのコンテナではやりません。守れる範囲を把握した上で使うことも、設計のうちだと思っています。

## 使い勝手

初回だけイメージのビルドで数分待ち、Claude へのログインが 1 回要ります。以後は自作の起動コマンド一発で、母艦とほぼ同じ操作感です。起動コマンドには「firewall の自己検証が通っていなければ起動を拒否する」チェックを入れました。firewall の初期化はこけてもコンテナ自体は走り続けてしまうので、「起動できた＝安全」ではないからです。

この環境にしてから、母艦で詰まっていた `yarn add` も E2E テストも普通に通るようになり、夜に作業を投げて朝に結果を見る運用ができるようになりました。

## まとめ

- 全権限の自走は隔離とセット。公式もコンテナ / VM の中でという立場です
- 隔離の要点は 3 つ。母艦への書き戻しを許さない、認証情報は被害範囲を限定した形だけ、通信は許可した宛先だけ
- firewall の守備範囲は正しく把握して割り切る

ここまでが設計の話です。ただ、実際に使い始めると「コンテナの中の Claude だけ URL がリンクにならない」「スクリーンショットが渡せない」といった、設計時には見えなかった細かい不便が出てきました。その潰し込みは[後編](/blog/claude-code-devcontainer-tuning)に書きます。
