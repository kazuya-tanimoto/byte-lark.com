# インシデント対応手順（運営者向け）

最終更新: 2026-06-14

本ファイルは byte-lark.com で**何かおかしなこと（サイトの書き換え・連絡先や個人情報の漏えい・サイト停止・認証情報の流出）が起きたとき**に、運営者が慌てず初動を取るための最低限の手順書です。site-plan.md の R-11 に対応します。

> この手順書は Claude がドラフトしたものです。運営者がレビューし、自分の運用実態に合わせて加筆・修正してください。

---

## 0. まず前提（このサイトの構成を知っておく）

対応を判断するうえで、今のサイトが「何を持っていて、何を持っていないか」を押さえておくと落ち着いて動けます。

- **公開はすべて静的ファイル**：Astro で事前ビルド（SSG）した HTML/CSS/JS を Cloudflare Workers が配信しているだけ。サーバー側で動くプログラムやデータベースは**今はない**（`wrangler.jsonc` の `assets` で `./dist` を配信）。
- **正本は GitHub の Git リポジトリ**：サイトの中身（記事・コード）はすべて Git にある。だから**改ざんされても、正しいコミットから作り直して上書きデプロイすれば元に戻せる**。
- **サーバー側に保存する個人情報はない**：Contact は Worker フォーム（`/api/contact`、Turnstile 検証 + Resend で `info@byte-lark.com` へ通知）。入力（氏名・メール・本文）はメール転送するだけで DB 等に保存しない。平文メールアドレスは公開していない（FR-29 でフォーム化、`mailto` 撤去済み）。
- **アクセス解析は Cloudflare Web Analytics（Cookieless）**：個人を識別する情報は集めていない。
- **公開ドメインは移行前**：現時点では `*.workers.dev` の branch alias で動作確認中。カスタムドメイン `byte-lark.com` への切替は Phase 1d（公開）で実施予定。

この構成のおかげで、現段階のインシデントは**「表示の改ざん」と「サイト停止」が主リスク**で、利用者の個人情報漏えいリスクは低い、という前提で読んでください。Contact フォーム（Worker + Resend、Phase 1b で導入済み）が動いているため、後述の「認証情報の漏えい」（Turnstile / Resend の secret）の重みが増しています。

## 1. 対応者・連絡先

法人化後（2026/06〜）も当面は一人体制のため、**対応者 = 運営者本人のみ**です。

| 役割 | 担当 | 連絡先 |
|---|---|---|
| 一次対応・意思決定・復旧 | 運営者（谷本） | tanimoto@byte-lark.com |
| サイト配信 | Cloudflare（Workers / アカウント所有者 = 運営者） | Cloudflare ダッシュボード |
| ソース管理 | GitHub（リポジトリ所有者 = 運営者） | GitHub 通知 |

> 法人化後（site-plan §13）は、ここを組織の連絡網・エスカレーション先に置き換える。複数人体制になったら「最初に気づいた人 → 誰に連絡するか」を1行で足すこと。

外部に説明・通報が必要になり得る相手（発生したときに思い出すためのメモ）：

- ドメインレジストラ / DNS 管理元（ドメイン乗っ取り時）
- Cloudflare サポート（アカウント侵害・不正請求時）
- 個人情報保護委員会・本人通知（個人情報の漏えいが実際に起きた場合。今の構成では基本的に該当しないが、フォーム導入後は要検討）

## 2. 監視の方針（push 型・自動検知ファースト）

**原則：平常時は運営者の操作ゼロ。異常があったときだけ通知（push）が飛んでくる形にする。**「定期的に複数のコンソールを見に行く（pull）」運用は、見落とすし続かないので採らない。人手は、自動化できないごく一部に絞る。

検知したいものと、それぞれの push 手段・有効化タイミングを整理する。

| 何を検知 | push の手段 | 種別 | 有効化 |
|---|---|---|---|
| 依存ライブラリの脆弱性・秘密情報の commit 混入（＝改ざんの入口） | GitHub の Dependabot / Secret scanning / Push protection → メール通知 | サービス純正 | **今すぐ可**（設定するだけ） |
| サイト停止・改ざん（表示書き換え）・TLS 証明書の期限 | 監視スクリプトを **Xserver の cron** で定期実行 → 異常時のみ**メール + Slack** に通知 | 自作・独立インフラ | Phase 1d（公開時に本番 URL へ向けて点火） |
| 死活監視の二重化（補完） | UptimeRobot 等の外形監視 → メール / Slack | 外部サービス | Phase 1d（任意・推奨） |
| Cloudflare アカウントの不正ログイン・設定変更 | 無料の push 手段なし → 2FA 必須化 + Audit Log を年数回だけ目視（§5） | 人手が残る唯一の点 | 今すぐ + 随時 |

### なぜ Xserver の cron を監視の主役にするか

サイトを配信している Cloudflare とは**別系統**の、運営者が既に契約している Xserver の cron でスクリプトを回すのが、この用途では一番筋が良い。

- **独立インフラ**：監視する側（Xserver）と監視される側（Cloudflare）が別。片方が落ちても、もう片方が気づける（監視が監視自身の道連れにならない）。
- **無料・既契約**：追加コストなし。Xserver の cron は shell・PHP の両方を実行でき、外向き curl も使える前提（運営者確認済み）。
- **確定的**：死活・文字列照合（改ざんカナリア）・証明書期限は決め打ちのスクリプトで十分。AI 判断は不要で、誤検知も少ない。

監視スクリプトがやること（実装は Phase 1d）：本番 URL を curl で叩き、(1) HTTP 200 か、(2) 想定の文字列（例：`<title>byte-lark.com</title>` や `byte-lark`）が残っているか＝改ざんカナリア、(3) セキュリティ/配信ヘッダが想定通りか、(4) TLS 証明書の残日数、を確認し、**異常時だけ通知**する。1 回の失敗で鳴らさず「2 回連続失敗で通知」等のしきい値を入れて誤報を抑える。これらの取得は実機（branch alias）で動作確認済み。

通知は **メール + Slack（Incoming Webhook）の二重**にする（メール＝証跡が残る／ Slack ＝スマホへ即時）。運用上の決めごと：

- **Slack の Webhook URL は秘密情報**。漏れると第三者が同チャンネルに投稿できる。スクリプトに直書きせず Xserver 側の環境変数か権限を絞ったファイルに置き、**リポジトリには commit しない**（GitHub の Secret scanning とも整合）。
- 異常時のみ・しきい値付きで鳴らす（アラート疲れ防止）。
- **「監視自身の死活を別サービスで見張る（dead man's switch）」は本構成では不要**と判断する。監視スクリプト・cron が止まる原因は実質 (a) 自分でスクリプト/cron を壊す、(b) Xserver 自体の障害・契約停止、の 2 つ。(a) は変更後に一度手で実行して確認すれば防げる。(b) は Xserver 側がインフラを監視・復旧しており、かつ**業務メール（@byte-lark.com）も同じ Xserver に同居**（MX が `sv16806.xserver.jp` 直指し）しているため、サーバー/契約が完全に止まればメール不通で嫌でも気づく。外部監視を増やすより構成をシンプルに保つ方を採る。

> 補足：本格的な監視は本番ドメインを対象にしてこそ意味があるため、Xserver cron / UptimeRobot の点火は**カスタムドメイン公開（Phase 1d）に合わせる**。それまで（branch alias / noindex 段階）に今すぐ入れるのは、下の GitHub 設定だけでよい。実装は Phase 1d の監視 PBI（`draft-phase1d-domain-launch.md` の「公開後の監視セットアップ」）で行う。

### 今すぐやること（無料・5分・サービス純正の push）

GitHub の **Settings → Code security and analysis** で次を有効化する（運営者の管理画面操作）。

1. **Dependabot alerts**（依存ライブラリの既知脆弱性をメール通知）
2. **Secret scanning** + **Push protection**（API キー等を commit しようとした瞬間に検知・ブロック）

正本である Git が汚れる前に止めるのが一番効く。public リポジトリなので無料。

> Claude を cron で回す案（claude.ai のクラウド routine）も技術的には可能だが、Claude 契約に依存し「監視自身が止まったら無通知」になるため、**主役ではなく任意の補助**（例：週次の総合レビュー）に留める。死活・改ざんの一次検知は Xserver cron に任せる。
>
> Phase 1b で Contact フォーム（動的 Worker）が入ったら、レート制限・Turnstile 検証ログの監視を監視スクリプトに足す。

## 3. 共通の初動フロー

種類を問わず、まずこの順番で動きます。**「止める → 残す → 直す → 振り返る」**です。

1. **初動（封じ込め・証拠保全）**
   - 慌てて消さない。**まず状態を記録**：おかしい画面のスクリーンショット、URL、気づいた時刻、Cloudflare/GitHub の該当ログを保存する。直してしまうと原因調査ができなくなる。
   - 被害が広がるなら止める：必要なら Cloudflare 側で一時的にサイトを止める / メンテ表示にする（手段は §6 各ケース）。
2. **調査（何が・どこから・いつ）**
   - 入口を特定：GitHub のコミット履歴・デプロイ履歴・Cloudflare のアクセスログから、いつ・何が変わったかを追う。
   - 影響範囲を特定：表示だけか、認証情報まで届いているか、利用者データに触れるか。
3. **復旧（正しい状態に戻す）**
   - 原則は**「正本（GitHub の正しいコミット）から作り直して上書きデプロイ」**。改ざんされた配信物を手で直すのではなく、クリーンなソースから再生成する。
   - 漏れた鍵があれば**無効化＋再発行（ローテーション）**してからデプロイ。
4. **報告・振り返り（記録と再発防止）**
   - 時系列を1枚にまとめる：いつ気づき / 何が起きて / どう直したか。
   - 法人化前は社内報告先が運営者本人なので、**この手順書の末尾か別メモに記録を残す**。利用者・取引先に影響が及んだ場合のみ、必要な範囲で連絡する。
   - 再発防止を1つ決めて実行（監視追加・権限見直し・手順修正など）。

## 4. 深刻度の目安

動き方の温度感をそろえるための目安です。厳密な定義より「すぐ動くか / 落ち着いて調べるか」の判断に使います。

| レベル | 状況の例 | 動き方 |
|---|---|---|
| 高（即対応） | サイトの内容が書き換えられている / 認証情報（Cloudflare・GitHub・APIキー）が漏れた / 利用者の個人情報が外に出た | その場で封じ込め開始。他の作業を止める |
| 中（当日中） | サイトが落ちている・極端に重い / 不審なデプロイ履歴がある | 当日中に原因特定と復旧 |
| 低（計画的に） | 依存ライブラリの脆弱性アラート / スパム的な大量アクセス（被害なし） | 通常の作業サイクルで対応 |

## 5. Cloudflare ダッシュボードでのセキュリティイベント確認手順（概要）

> 画面名は Cloudflare 側の更新で変わることがある。見つからないときは管理画面の検索で「Security」「Analytics」を引く。

1. **Cloudflare にログイン** → 対象アカウントを選ぶ。
2. 配信は **Workers & Pages → `byte-lark`**（`wrangler.jsonc` の `name`）。
   - **Deployments / バージョン履歴**を開く：身に覚えのないデプロイがないか確認。あれば、それが改ざんの入口。直前の正常バージョンに**ロールバック**できる。
   - **Logs / Observability**：直近のリクエストやエラーの傾向を見る。
3. **トラフィック異常の確認**：アカウントの **Analytics & Logs**（カスタムドメインを Cloudflare 管理下に置いた後はゾーンの **Security → Events** が使える）。
   - リクエスト数の急増、特定 IP / 国からの集中、ブロック済みリクエストの内訳を見る。
4. **アカウント自体の安全確認**：
   - **My Profile → Audit Log**：自分以外の操作・設定変更がないか。
   - **2要素認証（2FA）が有効か**を確認。無効なら今すぐ有効化（侵害時の最優先）。
   - **API トークン**一覧を確認し、不要・心当たりのないトークンは失効させる。

> 補足：ゾーン単位の WAF / セキュリティイベントは、ドメインを Cloudflare のネームサーバー管理下に置く（Phase 1d）と本格的に使える。それまでは Workers のデプロイ履歴とアカウントの Audit Log が主な確認対象。

## 6. ケース別の手順

### 6.1 サイトが書き換えられている（改ざん）

1. **初動**：改ざん画面のスクショ・URL・時刻を保存。
2. **入口の特定**：
   - GitHub のコミット履歴（`git log`）に身に覚えのない変更はないか。
   - Cloudflare の Deployments に身に覚えのないデプロイはないか。
   - → どちらかが侵害経路。GitHub 側なら**アカウント侵害**を疑い、Cloudflare 側なら**Cloudflare 認証情報の侵害**を疑う。
3. **封じ込め**：侵害された経路の**認証情報を即変更**（GitHub パスワード/トークン、Cloudflare パスワード/API トークン、それぞれ 2FA 確認）。
4. **復旧**：正しいコミットから再ビルドして上書きデプロイ、または Cloudflare で直前の正常バージョンにロールバック。
5. **報告**：時系列を記録、入口を塞いだことを確認（漏れたトークンの失効・再発行まで完了して初めて復旧）。

### 6.2 連絡先・個人情報の漏えい

1. **何が出たかを切り分ける**：
   - 以前公開していた `mailto`（平文メール）は FR-29 のフォーム化（Phase 1b）で撤去済み。現在サイト上に平文の問い合わせアドレスは出していない。
   - 本当に守るべき情報（受信したメール本文、将来フォームで受け取る問い合わせ内容など）が外に出たかを確認する。
2. **今の構成では利用者データを保存していない**ため、サイト経由の大規模漏えいは基本的に起きない。漏えいが疑われるとすれば**メール受信側（運営者のメールボックス）や認証情報の侵害**が起点。→ 6.4 へ。
3. 実際に第三者の個人情報が漏れた場合は、**範囲の特定 → 本人への連絡 → 必要に応じて個人情報保護委員会への報告**を検討（法人化後は社内手順に従う）。

### 6.3 サイトが落ちている / 応答しない

1. **本当に落ちているか確認**：別回線・スマホ回線でアクセス、外形監視（UptimeRobot 等）の結果を見る。自分のネット環境の問題のことも多い。
2. **切り分け**：
   - Cloudflare 障害か？ → Cloudflare のステータスページを確認。
   - 自分のデプロイで壊したか？ → 直近のデプロイをロールバック。
   - DNS / ドメインの問題か？（カスタムドメイン公開後） → ネームサーバー・DNS レコードを確認。
3. **復旧**：原因に応じてロールバック or 設定戻し。Cloudflare 側の広域障害なら復旧を待つしかない（その旨を記録）。

### 6.4 認証情報（パスワード・トークン・APIキー）の漏えい

最も波及が大きい類型。**「無効化が最優先、調査は後」**。

1. **即無効化（ローテーション）**：
   - GitHub：漏れた Personal Access Token / Deploy key を失効、パスワード変更、2FA 確認。
   - Cloudflare：API トークンを失効・再発行、パスワード変更、2FA 確認、Audit Log で不正操作確認。
   - （Phase 1b 以降）Worker secret（Resend の API キー等）：`wrangler secret` で再設定し、サービス側（Resend）でも旧キーを失効。
2. **混入経路を塞ぐ**：もしリポジトリに秘密情報を commit してしまったケースなら、その鍵は**履歴から消しても漏れた前提でローテーション**する（消すだけでは不十分）。GitHub の Push protection を有効にして再発防止。
3. **影響調査**：漏れた鍵で何ができたか（デプロイ・メール送信・課金など）を洗い、被害有無を確認。
4. **報告**：対応内容を記録。

## 7. 平常時にやること

監視は §2 の方針で**自動 push 化**するのが目標なので、平常時の手作業は最小限。状態を 2 つに分けて書く。

### 自動で飛んでくる（運営者の操作不要）

- 依存の脆弱性・秘密情報の混入 → GitHub からメール（要・初期設定。§2「今すぐやること」）
- サイト停止・改ざん・証明書期限 → Xserver cron の監視スクリプトからメール / webhook（Phase 1d で点火）

→ これらは**通知が来たときだけ動く**。来なければ正常、が原則。

### 自動化できず人手が残る（年数回・公開後）

- [ ] Cloudflare：身に覚えのないデプロイ / Audit Log の不審操作がないか（無料では push 不可のため目視。年数回でよい）
- [ ] Cloudflare / GitHub：2要素認証が有効か、不要な API トークンが残っていないか
- [ ] バックアップ：Git が GitHub + ローカルに揃っているか（バックアップ方針は R-13 で別途整備予定。本ファイルは復旧の入口が Git である前提に立つ）

> GitHub のセキュリティ通知（§2）を有効化していれば、依存・秘密情報のチェックは自動。「アラートが来ていないこと」が確認になるので、上の人手チェックから外してある。
