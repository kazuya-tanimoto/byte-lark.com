## 語彙の傾向

（例: 「〜だと思う」より「〜だろう」を好む、英単語はカタカナ化しない、など）

- 和文と半角英数の間にスペースを入れない（「Claude Code で」→「Claude Codeで」）。数字の前後も同様（「この 3 つ」→「この3つ」）。コードブロック内は対象外。既存公開記事も詰めに統一済み（2026-08-16 運営者決定）
- 手元のマシンは「手元のMac」と呼ぶ。「母艦」は使わない（2026-08-16 運営者決定）。連呼を避けるため、記事内では初出だけ「手元のMac」とし、以降は文脈が明確なら「Mac」だけでよい。対比が直前の文で確立していれば省略する（2026-08-20 運営者指示）

## 構成の癖

（例: 結論先出し、コード例多め、など）

- 1〜2 文ごとに行末スペース 2 つで改行する。長い段落で詰めない（2026-08-15 PHASE1E-003 ドラフトへの運営者指摘を受けた既存記事の観察）

## 避ける表現

（例: 過剰な敬語、「させていただく」系、など）

- 他者の選択を腐す言い回し（「mailto は無いですよね。普通に。」等）。自分がなぜ採用しなかったかだけを淡々と書く（2026-08-01 PHASE1B-009 ドラフトへの運営者指摘）
- 地の文での体言止めの多用（「不採用。」「〜だけ。」等）。文を短くするときも文末は です・ます で言い切る。体言止めは効かせたい所にたまにだけ。箇条書きの中は言い切りで可（2026-08-02 同上）
- 読者に前提知識を仮定した説明（「管理するサーバーを増やしていない」等）。仕組みの前提（配信は何がやっているか、処理はどこで動くか）を先に普通の言葉で説明してから本題に入る。最低限の IT 知識で通じるかを毎回自問する（同上）
- 上記「前提知識を仮定しない」の適用先は仕組みの前提だけ。静的サイト・エスケープ・レスポンス等の Web 開発基礎用語をふわっとした日本語（「窓口」「置き場」「返事」等）に言い換えることには適用しない。tech 記事の対象読者はエンジニア（当該分野の未経験は可）（2026-08-02 PHASE1B-009 リライトへの運営者指摘）
- 固有の仕組みを曖昧な代名詞（「自作プログラム」等）で呼び続けない。正式名称を初出で 1 回定義し、以後その名前で使い回す（同上）
- ドラマチックな比喩・擬人化（「コンテナに閉じ込める」「暴れる」「晒される」等）。事実を普通の動詞で書く（「隔離する」「触れる」）（2026-08-15 PHASE1E-003 ドラフトへの運営者指摘）
- 決め台詞・アフォリズム（「X は Y とセットでやるものです」「ポイントは『漏れない』を目指すのではなく〜」「〜も設計のうち」等の、うまいこと言う一文）。直前の文で内容が言えていれば削除、言えていなければ平叙文に開く（同上）
- 断言の短文でキメる・倒置（「これが通らない限り、自走はさせません。」「壊れるのが、〜だからです」等）。普通の語順の です・ます に戻す（同上）
- コンサル調のフレーミング（「3つの原則」「仕掛けは〜」等の大仰なラベル）。「決めたこと」「やっていること」程度の平易な言葉にする（同上）
- 実感の捏造。くだけた挿入（「ぶっちゃけ」「（〜だし）」等）は、本文に既に書かれている実感の言い換えとしてのみ足してよい。運営者が実際に感じたか分からない感想・感情を新規に創作しない（2026-08-15 同上）
- 経緯・検討過程の創作。「〜でしのいでいた」「〜と考えたこともあった」のような経緯・思考の記述は、運営者に事実確認できたものだけ書く。読者の疑問への先回りを本人の思考過程として書かない（2026-08-16 PHASE1E-003 前編リライトへの運営者指摘）
- 疑問形・「そもそも〜か」型の見出し（「そもそも何に困っていたか」等）。見出しは名詞句か平叙の言い切りにする（同上）
- 「危険側」「安全側に倒す」等の「〜側」語法、「手が届く」等のこなれない言い回し。普通の動詞・形容に開く（「危険なオプション」「触れる」）（同上）
- 話の本筋に効かない内部名・固有名（Seatbelt 等）。読者が知らなくても話が通る名前は出さない（同上）
- ひらがなが長く連続する文末（「〜ていないといけないわけです」等）。読みにくいので言い換える（同上）
