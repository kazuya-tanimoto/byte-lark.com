# 執筆ワークフロー

byte-lark.com ブログ記事の作成フロー。Claude Code（または claude.ai）と対話しながら記事を書く。

## フロー概要

```
[1] テーマを思いつく
  ↓
[2] Claude にヒアリング依頼（テーマ + 一言の動機）
  ↓
[3] Claude が質問を返す（5-10 問）
  ↓
[4] 運営者が回答（テキスト / 音声文字起こし）
  ↓
[5] Claude が深掘り質問 ⇄ 運営者が回答（根拠が揃うまで繰り返す）
  ↓
[6] Claude が Markdown ドラフト生成（draft: true）
  ↓
[7] Claude が /article-review（1 回目）→ 指摘を自分で反映（事実の指摘は調べる → 削る → 聞く）、「公開可能」まで繰り返す
  ↓
[8] 運営者がレビュー・リライト
  ↓
[9] /article-review（2 回目）→ Claude が仕分け（直す／出さない／聞く）→ 反映
  ↓
[10] yarn fonts でフォントを作り直す → draft: false に変更
  ↓
[11] 公開。文体プロファイル更新
```

## 1. テーマ決定

何でもいい。「最近ハマったこと」「仕事で学んだこと」「読んだ本の感想」など。

カテゴリの目安:
- `tech` — 技術ネタ（言語、ツール、設計、AI、インフラ）
- `life` — 仕事術、キャリア、書籍、日常

## 2. ヒアリング依頼

Claude に以下の形式で伝える:

```
テーマ: ○○○
動機: なぜこれを書きたいか一言
カテゴリ: tech or life
```

## 3. Claude のヒアリング質問（SOP プロンプト）

Claude は以下の観点で 5-10 問を返す:

1. **読者像** — 誰に向けて書く？ 前提知識レベルは？
2. **結論** — 読者に一番伝えたいことは？
3. **構成** — 問題→解決？ 時系列？ 比較？
4. **具体例** — コード例やスクリーンショットは入れる？
5. **キー主張** — 「これだけは言いたい」ポイントは？
6. **反論想定** — 「それって○○じゃない？」への回答は？
7. **分量** — 短め（1000字）/ 普通（2000-3000字）/ 長め（5000字+）？
8. **トーン** — カジュアル / ニュートラル / フォーマル？
9. **参考情報** — URL、書名、ドキュメントなどあれば
10. **タグ候補** — どんなキーワードで見つかってほしい？

## 4. 回答

箇条書きでも一文ずつでも、音声入力のベタ打ちでもOK。Claude は文脈から汲み取る。

## 5. 深掘り（回答が浅いままドラフトに進まない）

Claude は回答を見て、浅い・具体性が足りない箇所に追加質問を返す。記事の根拠として十分になるまで質問 → 回答を繰り返してから、次のドラフト生成に進む。浅い回答のままドラフトを作ると、Claude が隙間を推測で埋めてしまい（経緯・実感の創作。profile.md「避ける表現」参照）、後のリライトが膨らむため。

深掘りが要る回答の目安:

- 評価・感想が形容詞だけで場面・根拠がない（「便利だった」→ どの作業の何がどう変わった？）
- 経緯・検討過程（なぜその構成にしたか、他に何を検討したか）が読み取れない
- うまくいかなかった点・制約への言及が空欄（無いなら「無い」と確認を取る）
- 記事が言及する実装・設定・計測の現物（ファイル・ログ・コマンド出力）の所在が未確認
- 比較対象・代替案に触れているのに、実際に検討したかが不明
- 原因を「設定 X だった」と書くのに、X が既定でそうなのか、運営者がいつ・なぜ変えたのかを確かめていない（PHASE1E-008 で既定オフの設定を、乗り換えただけで起きたように書いた実測）

## 6. ドラフト生成

Claude が以下を行う:
- `yarn new-post --slug <slug>` で雛形を生成
- frontmatter を埋める（`draft: true`）
- 本文を Markdown で書く
- 文体プロファイル（`docs/writing-style/profile.md`）を必読し、そのトーン・「避ける表現」を守って書く
- **執筆の直前に profile.md と直近公開記事 1〜2 本を読み直す**。セッション前半で読んだ記憶だけで書かない（PHASE1E-008 で骨組み時に読んだきり執筆日に照合せず、AI 臭の再発を見逃した実測）
- **運営者の回答・実装の現物から言えない経緯・感想・検討過程を創作しない**。材料に無いことは書かない。書きたければ先に調べ、調べて分からなければ書かない。「書いて【要確認】を付ける」は不可（「材料に無いことの扱い」節）。運営者に聞くのは同節の条件に当たるときだけで、書式と上限（3 件）も同節に従う。実感・場面の材料が足りずに記述が薄くなるならそれはヒアリング不足であり、薄いまま書かずに §5 の深掘りへ戻って運営者に質問する
- **書き上げたら natural-japanese スキル（プラグイン）の検査を必須で通す**：lint（`--genre` は記事に合わせる）と構造・読みやすさの点検を収束させ、profile.md「避ける表現」を 1 項目ずつ照合する。AI 臭が残っていない自信を持てるまで運営者に出さない
- article-review スキルの 9 軸（事実照合〜AI 臭）を満たす前提で書き、ドラフトを出す前に自己チェックする。レビューで初めて直すのではなく、初回ドラフトから考慮する

## 7. レビュー 1 回目（/article-review）

ドラフトを運営者に渡す前に、Claude が `.claude/skills/article-review`（`/article-review`）で全軸レビューする。

- subagent（general-purpose）で実行する。ドラフトを書いたコンテキストでの自己レビューは自分の文に甘くなるため
- 指摘はドラフト担当が自分で反映し、総評が「公開可能」になるまでレビュー → 反映を繰り返す。運営者の承認は取らない
- 「事実か」の指摘は「材料に無いことの扱い」節の順で処理する：自分で調べる → 材料にも無ければ削る → 本人しか知らず記事に要る文だけ【要確認】（書式・上限は同節）。指摘をそのまま運営者への質問にしない
- 運営者に渡すのは「公開可能」になったドラフト + 【要確認】の一覧（本文の 4 行をそのまま並べる）+ 【要写真】の一覧（本文の 1 行をそのまま並べる）。誤字・表記揺れ・事実の不一致は、この段階で潰しておく

## 8. 運営者レビュー・リライト

運営者が内容を確認し、自分の言葉で仕上げる。誤字・表記は 1 回目で潰れている前提で、内容の判断に集中する。本文が固まったら次へ。

リライトを Claude が代行する場合も §6 と同じゲートを通す（natural-japanese の検査 + profile.md 全項目照合を済ませてから運営者に出す）。

運営者フィードバックへの対応手順（必須。PHASE1E-008 で無承認の修正が発生した実測から）:

1. 運営者のリライト・回答をまずコミットして保全する
2. 疑問形の指摘には、修正より先に回答する
3. 修正方針（対象箇所と修正後の文面）を項目ごとに提案し、運営者の OK を待つ
4. OK が出た項目だけを反映する。OK の無い項目・回答が保留の項目には手を付けない
5. 承認された文面から変える必要が出たら、再提案して OK を取り直す。軽微でも黙って変えない

## 9. レビュー 2 回目（/article-review）

公開前に `/article-review` でもう一度全軸レビューする。運営者のリライトで入った誤字・表記揺れ・事実のずれを拾う回。

レビュー担当（subagent）には、本文が運営者のリライト済みであることと、それまでに運営者と確定した事項を渡す。

レビュー担当の報告は運営者にそのまま渡さない。Claude が次の 3 つに仕分けてから出す（PHASE1E-008 で指摘 16 件と確認 3 件を仕分けずに渡し、本文と見比べないと答えられない質問になった実測から）:

1. Claude が直す：行末スペース・表記揃え・数値の鮮度など、文を変えない直し。反映してから「変更」として報告する
2. 出さない：運営者が書いた文への言い回し・構成の提案、表示に影響しない体裁、確定事項と食い違う指摘。件数だけ実装ログに残す
3. 運営者に聞く：「事実か」の指摘は「材料に無いことの扱い」節の順（自分で調べる → 削る → 聞く）で処理し、残ったものだけ同節の 4 行書式で 3 件まで

運営者の文を変える直し（1 に当たらないもの）は §8 の対応手順に従い、文面を提案して OK を待つ。3 の回答と 1・2 の件数を実装ログに記録する。

## 10. フォントを作り直す（`draft: false` にする直前）

```bash
yarn fonts
```

配信しているフォントは「サイトに出てくる字だけ」に絞ってある（PHASE1D-010）。記事を足すと新しい字が増えるので、作り直さないとその字だけ端末任せの書体で描かれる。

- 回すのは**本文を書き終えて `draft: false` にする直前**。下書きのうちは本文がまだ動くので早く回しても無駄になる
- `yarn fonts` は「ビルド → 収録字の抽出と再生成 → ビルド」の 3 段。数十秒かかる
- 生成物（`src/assets/fonts/*-subset.woff2`）も記事と一緒にコミットする
- 回し忘れは CI（`yarn fonts:check`）が止めるが、そこで気づくと push をやり直すことになる

回し終えたら frontmatter を `draft: false` に変更する。

## 11. 公開と文体蓄積

- `draft: false` にすればビルドに含まれ公開される
- 公開後、その記事の文体特徴を `docs/writing-style/profile.md` に追記（任意）
- 蓄積が進むと、次回以降のドラフト精度が向上する

## 材料に無いことの扱い（ドラフト以降の決まり）

材料とは、取材メモ（docs/article-interviews/<slug>.md）・運営者の回答・実装の現物・公式 docs / ソースのこと。公式 docs や実装で確かめられることは Claude が自分で調べ、出典つきで書く。運営者には聞かない。

ドラフト以降は次の順で扱う（PHASE1E-008 と monotrip.jp で、確かめていない細部を書いて【要確認】を付け、レビューの指摘を仕分けずに運営者へ質問として流した実測から）:

1. ドラフト：材料に無いことは書かない。書きたければ先に調べる。「書いて【要確認】を付ける」は不可
2. レビューで「事実か」と指摘されたら、まず Claude が自分で調べる（公式 docs・実装・取材メモ）
3. 調べて分からず、材料にも無ければ、その文を削る
4. 運営者に聞くのは、本人しか知らず、かつその文が記事に要るときだけ。聞けるのは次の 2 種
   - 事実の正確さ：本文に書いた事実（環境・経緯・数値・設定）が本人の実際と合っているか
   - 主張の当否：本文の結論・評価を本人がそう思っているか
5. 聞くときは本文の文を丸ごと引用し、はい／いいえか選択肢で答えられる形にする。行番号だけで指さない

経緯・場面・感想を開いた形で聞くのは §3〜5 のヒアリングまで。ヒアリングの質問数はこの節では制限しない。

スクショ・写真の提供依頼は質問ではなく作業の依頼なので、【要確認】に入れず【要写真】という別の印で書く（monotrip.jp で 1 記事に写真 8 件の依頼があり、3 件の上限に当たった実測から分離）。無回答なら「載せない」しかなく、本文の記述が正しいかとは別の話。件数は記事の作りで決まるので上限は付けない。

件数の上限（補助。超える分は 3 に戻って削る）:

- 【要確認】：1 記事 3 件まで（§6〜7）。【要写真】は数えない
- レビュー 2 回目で運営者に聞く件数：3 件まで（§9）

【要確認】の書式（本文中、対象の文を含む段落の直後に置く。1 件 4 行）:

> 【要確認｜事実】
> 対象：「本文の文をそのまま引用」
> 質問：はい／いいえ、または選択肢で答えられる 1 文
> 無回答なら：対象の文をどう書き換えるか。または「対象の文を削る」

- 種別は 事実／主張 のどちらか
- 「無回答なら」は必須。運営者が答えずに §8 のリライトへ進んだら、その文面を適用して【要確認】を消す
- §9 で聞くときも同じ 4 行を使う（本文には書かず、報告に載せる）

【要写真】の書式（本文中、画像を置く位置に 1 行。撮影リストの番号と、何を撮るかを書く。写り込みの確認があれば添える）:

【要写真：撮影リスト No.1（ghostty の設定画面。ウィンドウ全体）】

- 運営者が提供したら画像に差し替える。提供が無ければその行を消し、本文は画像なしで成り立つ形にする
- 書式・件数・公開記事（draft: false）への残留は `yarn posts:check` が検査し、pre-push と CI（Quality Checks）で止まる（【要写真】は書式と残留だけで、件数は数えない）。印を付けずに書いた創作は機械では拾えないため、§7 のレビュー 1 回目で取材メモと突き合わせて拾う

## 画像・添付ファイルの置き場所

- 記事は画像の有無によらず常にフォルダ形式で作る: `src/content/posts/<slug>/index.md`（`yarn new-post` がこの形式で生成。posts 直下にフラットな `<slug>.md` を置かない）。画像は同じフォルダに同居（loader は `**/*.{md,mdx}` なのでフォルダ化しても収集される。URL は frontmatter の `slug` で決まるため変わらない）
- 本文からは相対パスで参照する（`![説明](./figure.png)`）。Astro のビルド時最適化（圧縮・ハッシュ名・width/height 自動付与）が効く。`public/` 置きは最適化が効かないため記事画像には使わない
- アイキャッチは frontmatter の `cover: ./cover.png`。ブログ一覧カード・記事ページ冒頭・og:image（1200×630 に自動変換）の 3 か所に自動反映される。元画像は縦横比 40:21（1200×630 以上）で作る
- AI 生成イラストを使う場合は、確定パレット「春空」（docs/design-direction.md §2）とブランドトーン（ヒバリ意匠）に寄せ、記事間で作風を揃える
- PDF など画像以外の添付は最適化対象外のため `public/files/<slug>/` に置き、絶対パスでリンクする（`[資料](/files/<slug>/xxx.pdf)`）
