# 記事レビュー

プロのテクニカルライター視点で記事を全面レビューし、指摘一覧を報告する。修正はしない——報告に対する運営者の承認を待ち、承認された項目だけを直す。

## 対象の特定

引数の記事パス / slug を使う。無ければ docs/pbi/INDEX.md の InProgress な記事 PBI から特定し、冒頭で「◯◯をレビューします」と明示する。

## 手順 1：材料を読む（レビュー開始前に全部）

- 記事全文 + frontmatter
- 記事が引用・言及する実装ファイル（worker/、src/components/、wrangler.jsonc 等）。記事内のコードは省略・改変されていることがあるため、必ず原本を開いて突き合わせる
- docs/writing-style/profile.md（文体ルール・避ける表現）
- 該当 PBI（ヒアリング結果＝読者像・トーン・分量の合意、受け入れ条件、技術メモの禁止事項）
- 記事タイプ（T1 エッセイ型 / T2 検索型など。定義は PHASE1B-007 / docs/article-backlog.md）

## 手順 2：7 軸レビュー（全軸実施）

| 軸 | 見るもの |
|---|---|
| 事実照合 | 技術的主張と実装・公式 docs の一致。引用コード・引用文書と原本の差分。リンク先の実在 |
| セキュリティ | secret 値・実メールアドレス・内部情報の混入。掲載コードの脆弱性・誤解を招く実装 |
| 構成 | 説明の流れの断線（登場した概念が最後まで繋がるか）。基礎用語の過剰説明と核心の仕組みの説明不足の逆転 |
| 文体 | profile.md（避ける表現・語彙の傾向）への抵触。曖昧な代名詞。冗長・不明瞭な表現 |
| 表記 | タイポ。用語・表記の揺れ（同じものを別名で呼ぶ）。和欧間・数字前後のスペース（詰めルール、profile.md 語彙の傾向）への違反・混在。行末スペース 2 つ（強制改行）の欠落・過剰 |
| メタタグ | title（T1＝メッセージ型 / T2＝検索キーワード先頭。`| byte-lark.com` サフィックス無し）。description 80-120 字・OGP 兼用。tags。slug。本文冒頭に h1 重複が無いこと |
| 読者適合 | PBI ヒアリングの読者像に対する難易度。読者に前提知識を仮定していないか |

## 手順 3：報告（この形式で出す）

1. 総評 1-2 文（公開可能か、要修正の件数）
2. 指摘一覧：重要度順（誤り・セキュリティ → 分かりづらい → 軽微）。各指摘に「位置 / 現状 / 問題 / 修正案」
3. セクション別判定表：記事の全セクション + frontmatter を列挙し、それぞれ 維持 / 修正 + 理由を明記
4. 締め：どの指摘を適用するか運営者に確認

## 禁止事項

- 一部セクションだけ見て「問題なし」と返す。判定表に載らないセクションを作らない（frontmatter・メタタグも 1 行として載せる）
- 実装ファイルを読まずに記事内コードを「正しい」と判定する
- 軽微な typo でも承認前に本文を直し始める
- 「前回レビュー済みだから」と軸を省く。省くときは理由を報告に明記する
- 外部リンクなど検証できなかった項目を黙って落とす。「未検証項目」として報告に載せる
