# 記事レビュー

プロのテクニカルライター視点で記事を全面レビューし、指摘一覧を報告する。修正はしない——報告を受けた側が直す。誰が承認するかは呼び出しの回で変わる（docs/writing-workflow.md §7 / §9）。

- 1 回目（ドラフト直後、呼び出し元＝ドラフト担当の Claude）：報告を受けたドラフト担当が指摘を反映し、総評が「公開可能」になるまでレビューを繰り返す。運営者の承認は不要。ただし運営者にしか分からない事実（経緯・感想・環境）は直さず「【要確認】」で本文に残す
- 2 回目（運営者のレビュー・リライト後）：報告に対する運営者の承認を待ち、承認された項目だけを直す

## 対象の特定

引数の記事パス / slug を使う。無ければ docs/pbi/INDEX.md の InProgress な記事 PBI から特定し、冒頭で「◯◯をレビューします」と明示する。

## 実行コンテキスト

ドラフトを書いたコンテキストでの自己レビューは自分の文に甘くなる。ドラフト担当はこのスキルを subagent（general-purpose）で実行し、報告だけを受け取る。運営者が `/article-review` を直接呼ぶ場合も、ドラフトを書いたセッションとは別の新規セッションで呼ぶ。

## 手順 1：材料を読む（レビュー開始前に全部）

- 記事全文 + frontmatter
- 記事が引用・言及する実装ファイル（worker/、src/components/、wrangler.jsonc 等）。記事内のコードは省略・改変されていることがあるため、必ず原本を開いて突き合わせる
- 記事が根拠にする公式ドキュメント・一次情報（URL）。記事内のエラー文・パス・コマンド出力の原本（ログ・実ファイル）
- docs/writing-style/profile.md（文体ルール・避ける表現）
- 該当 PBI（ヒアリング結果＝読者像・トーン・分量の合意、受け入れ条件、技術メモの禁止事項）
- 記事タイプ（T1 エッセイ型 / T2 検索型など。定義は PHASE1B-007 / docs/article-backlog.md）
- 既存の公開記事（`draft: false`）から直近 1-2 本（統一感軸の比較対象）

## 手順 2：8 軸レビュー（全軸実施）

| 軸 | 見るもの |
|---|---|
| 事実照合 | 技術的主張と実装・公式 docs の一致。引用コード・引用文書と原本の差分。リンク先の実在。主張の根拠が「観察した挙動」か「仕様（公式 docs・ソース）」かを区別し、観察だけで仕様を断定している箇所。一般論・調査結果に範囲付け（「一般に」「調査時点では」）が無い断定。エラー文・パス・コマンド出力が原本と一致するか |
| セキュリティ | secret 値・実メールアドレス・内部情報の混入。掲載コードの脆弱性・誤解を招く実装 |
| 構成 | 説明の流れの断線（登場した概念が最後まで繋がるか）。基礎用語の過剰説明と核心の仕組みの説明不足の逆転。初出の固有名・自作コマンドに役割の定義があるか。抽象説明で終わる段落（何を見て何が分かったかが無い）。主語・対象の欠落。読者の再現に効かないコード解説 |
| 文体 | profile.md（避ける表現・語彙の傾向）への抵触。曖昧な代名詞。冗長・不明瞭な表現 |
| 表記 | タイポ。用語・表記の揺れ（同じものを別名で呼ぶ）。和欧間・数字前後のスペース（詰めルール、profile.md 語彙の傾向）への違反・混在。行末スペース 2 つ（強制改行）の欠落・過剰 |
| 統一感 | 既存公開記事とのトーン・表記の一致（言い切り方・呼称・改行スタイル・用語の揃い） |
| メタタグ | title（T1＝メッセージ型 / T2＝検索キーワード先頭。`| byte-lark.com` サフィックス無し）。description 80-120 字・OGP 兼用。tags。slug。本文冒頭に h1 重複が無いこと |
| 読者適合 | PBI ヒアリングの読者像に対する難易度。読者に前提知識を仮定していないか。まとめが筆者の構成限定（特定のファイル名・自作コマンド名）になっていないか。未公開記事の予告・リンク |

## 手順 3：報告（この形式で出す）

1. 総評 1-2 文（公開可能か、要修正の件数）
2. 指摘一覧：重要度順（誤り・セキュリティ → 分かりづらい → 軽微）。各指摘に「位置 / 現状 / 問題 / 修正案」
3. セクション別判定表：記事の全セクション + frontmatter を列挙し、それぞれ 維持 / 修正 + 理由を明記
4. 未検証項目：実行環境から確認できないもの（外部 SaaS の挙動、自作コマンドの仕様、手元の Mac の環境変数 等）には「ローカルセッション向け依頼文」を添える。依頼文は自己完結にする（前提知識ゼロで打てるコマンド + 結果の報告形式）
5. 締め：どの指摘を適用するか運営者に確認（2 回目）。1 回目は反映後に再レビューする旨を書く

## 禁止事項

- 一部セクションだけ見て「問題なし」と返す。判定表に載らないセクションを作らない（frontmatter・メタタグも 1 行として載せる）
- 実装ファイルを読まずに記事内コードを「正しい」と判定する
- 軽微な typo でも承認前に本文を直し始める
- 「前回レビュー済みだから」と軸を省く。省くときは理由を報告に明記する
- 外部リンクなど検証できなかった項目を黙って落とす。「未検証項目」として報告に載せる
