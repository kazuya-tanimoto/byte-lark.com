# カバー画像生成

`tools/imagegen/generate_image.py`（Gemini API）で線画調のカバー画像を生成し、評価 → 運営者選定 → 記事配置 → 検証まで行う。

## デザイン方針（2026-09-16 改定）

経緯：2026-08-18 に「tech カバーが一覧で全部同じ画像に見える」問題へ、固定＝濃紺の設計図調＋雲雀署名 / 可変＝主役モチーフ＋アクセント色 1 色、の暫定方針を入れた。4 本作って 400px で並べた結果、色を 1 色差し替えても濃紺の背景が画面の 7 割を占めて同じに見えることが分かった（区別できたのは面積の大きい部品に色を載せた 2 本のみ）。署名サイズの雲雀は 400px では見えず、ブランドの役割も果たしていなかった。2026-09-16 に運営者判断で固定部分を減らした。

- 共通（ブランドの役割）：手描き風の線画イラストという様式だけ。面はほとんど塗らず、単純化した形で描く
- 可変（記事の識別）：背景色・構図・主役モチーフ・アクセント色を記事ごとに変える。濃紺の設計図調は選択肢の 1 つで、既定ではない
- 雲雀は任意。入れるなら隅に小さく 1 羽、円形ストロークは付けない（主役サイズ＋円形ストロークはロゴ画像に見える）。入れる場合の参照画像は `reference-bird.png`
- 他社ロゴ：生成 AI に描かせない（形が崩れる）。使うなら実物ファイルを後から合成する。ライセンスは都度確認する（Apache-2.0 は §6 で商標の使用を許諾していない。出所表示の通常の範囲かどうかを見る）。ghostty-herdr-migration では合成まで試した上で運営者が「無くてよい」と判断した
- 色の決まり：
  - 緑は tech カバーに使わない。カテゴリチップの緑＝Life と同一カード上で意味が衝突する（design-direction.md §2、BlogCard.astro）。Life 記事カバーに温存
  - 彩度は春空の世界観に合わせ淡め。蛍光系は不可。カバーはコンテンツ扱いでサイトトークンの縛りは無いが、世界観からは外さない
  - 色名が違っても同系に見える組み合わせがある（濃紺の上の淡い藤色と桜色）。色は名前でなく 400px 比較で決める
- 判定基準：400px 縮小で既存カバーと並べ、一目で別画像と分かること（評価手順 2 で実施）
- 既存カバーの系統：濃紺の設計図調 4 本（building-this-blog / contact-form / claude-code-devcontainer / claude-code-devcontainer-tuning）、木目の机上イラスト 1 本（incorporating-bytelark）、灰白の紙にインク線画 1 本（ghostty-herdr-migration）

## 進め方（構図の探索 → 深掘り）

1. 構図の違う案を 3 つ書き、1 案 1 枚ずつ生成する（Flash 3 枚 ≒ 45 円）。色や細部の違いではなく、構図（横移動の場面 / 俯瞰の地図 / 静物のクローズアップ、など）を変える
2. 400px 比較を作って運営者に見せ、進める案を選んでもらう
3. 選ばれた案をそのまま採用するか、変えたい点を反映して数枚を追加生成するかは運営者判断
4. 生成後の合成・修正（白い部分の埋め、ロゴの合成、縮小）は Pillow で行い、手順を scratchpad のスクリプトに残す

## 実行前の確認（毎回）

- 生成は有料（Flash 2K 1枚 $0.101 ≒ 15円 / Pro $0.134）。実行前に枚数と概算費用を提示して承認を得る
- モデルは Flash（`gemini-3.1-flash-image`、スクリプト既定）を主力にする。運営者の選好も Flash。Pro は注記がきれいだが線が細く、比較用の少数のみ
- 参照画像は雲雀を入れるときだけ `reference-bird.png` を渡す。入れないなら `-r` は不要

## 生成

```fish
cd tools/imagegen
.venv/bin/python generate_image.py -n 3 -p prompt_<記事slug>.txt \
  -r ../../docs/design-drafts/covers/reference-bird.png \
  -o out/<記事slug>
```

- 出力先は `-o out/<記事slug>` で必ず記事ごとのサブディレクトリを指定する（`out/` 直下にフラットに出さない。どの画像がどの記事か分からなくなるため）。slug は `src/content/posts/` のフォルダ名に合わせる
- プロンプトは記事ごとに `prompt_<記事slug>.txt` を新調する（デザイン方針節の共通・可変に従う。雛形は濃紺の設計図調なら `prompt_claude-code-devcontainer.txt`、明るい紙の線画なら `prompt_ghostty-herdr-migration.txt`）。「後でロゴを置くので隅を空けておく」のような指示は、その領域が白い矩形として描かれる（ghostty-herdr-migration で実測）。空けたい場所は指示せず、生成後に Pillow で埋める。`prompt_logo.txt` は雲雀主役の旧様式。新調するときの鉄則：1案 = 1リクエスト（複数案を1枚にまとめない）、注記の文字は英数字のみ許可（全面禁止も日本語も破綻する）
- 出力は `out/<記事slug>/` に raw（16:9 2K）と `*_cover.png`（40:21 センタークロップ、2752×1444）が並ぶ

## 評価と選定

1. 各候補の `*_cover.png` を原寸で確認：（雲雀を入れた場合）鳥の造形がロゴに忠実か／注記のラベル重複・文字化け・値のない寸法線／構図バランス
2. 400px 幅に縮小した画像も作って確認（ブログ一覧カード相当。細線・小要素はここで消える）。既存記事の cover と横並びにし、一目で別画像と分かるかを確認する（デザイン方針節の判定基準）
3. 候補を順位と根拠つきで運営者に提示し、選定を仰ぐ（勝手に決めない）

## 記事への配置

- 記事をフォルダ形式にし（`src/content/posts/<slug>/index.md`）、選定画像を同フォルダに `cover.png` で配置、frontmatter に `cover: ./cover.png`（詳細: docs/writing-workflow.md §画像）
- コミットする cover は 2000×1050 に縮小（Pillow LANCZOS）。2752 原本と縮小版は `out/<記事slug>/`（gitignored）に残す

## 検証と既知の罠

- CLAUDE.md §7 の検証ゲートを全て実施（ローカル + CF preview のデスクトップ/モバイル表示、CI green）
- カバー付き記事のパス変更（改名・フォルダ化）は CF ビルドキャッシュで ImageNotFound になる既知パターン。CF が赤になったら Clear Cache
- サブディレクトリ起点のセッションは repo 本体への Bash 書き込み（git 含む）が sandbox で塞がれる。その場合は bash スクリプトを書き出して運営者ターミナルで実行してもらう
